# RL implementation review — September 11, 2026

Review of the current working tree, including uncommitted changes. No production
implementation was changed during this review. The pending job was not altered.

## Findings

### 1. [P1] Resume can silently attach an adapter to the wrong SFT weights

Locations: `llava/train/rl/train_grpo.py:189`, `:198`, `:244`, `:313`.

`load_policy` constructs the base from the current CLI path before attaching the
saved adapter. The resume guard checks only the string `RL_OBJECTIVE`; it does
not compare the saved adapter's base model identity, resolved symlink target,
tokenizer or reward/renderer configuration with the requested run. Repointing
`sft_model` and reusing a run name can therefore load the old adapter and optimizer
onto a different same-shaped SFT model. Disabling the adapter then also supplies
the wrong reference policy for that resumed experiment.

Reproduced with two tiny same-architecture Qwen checkpoints initialized with
different weights: an adapter saved from A loaded on B without error, and the
result retained B's different base embeddings. Save a durable base/protocol
identity and validate it on resume; permit intentional changes only explicitly.
The queued fresh run pins its SFT path and does not exercise this failure case.

### 2. [P2] An interrupted checkpoint marker prevents fallback to a valid checkpoint

Locations: `llava/train/rl/train_grpo.py:227`, `:244`.

`state.json` is created directly in the final checkpoint directory, and mere file
existence makes `latest_checkpoint` select it. A timeout or filesystem failure
between opening and finishing that file leaves an empty/truncated marker. Resume
then raises a JSON error rather than falling back to the previous complete save.
The optimizer/scheduler/adapter files are also not checked by the selector.

Reproduced selection of a newest checkpoint with `state.json` containing only
`{`, followed by `JSONDecodeError`. Write and validate a complete temporary
checkpoint before publishing it atomically, and skip invalid candidates.

### 3. [P2] Disabling periodic saves also disables the final checkpoint

Location: `llava/train/rl/train_grpo.py:615`.

With `--save_steps=0`, periodic saves are skipped, and the final condition is
`max_steps % max(0, 1) != 0`, which is always false for integer step counts.
A successful training run therefore finishes without any adapter checkpoint.
The actual final-save expression was checked with 500 steps and returned false.
Handle final saving independently from the periodic interval. Defaults of 25
are unaffected.

### 4. [P2] Empty validation shards break distributed collective ordering

Locations: `llava/train/rl/train_grpo.py:397`, `:412`, `:580`, `:612`.

When validation contains fewer rows than ranks, a rank can receive no rows and
skip validation while others enter its `reduce_sum`. They then either wait for
an absent collective or collide with a different collective from training.
Returning `{}` early inside `run_validation` has the same problem. This is not
just a theoretical branch: a two-rank CPU probe with one validation prompt made
rank 0 time out at the reduction while rank 1 returned an empty result.

Every rank must enter the same evaluation collectives, including ranks with
zero samples. The current 32 prompts / 4 GPUs configuration has nonempty shards
and does not trigger this case.

### 5. [P2] Per-modality PG/KL metrics depend on the microbatch partition

Locations: `llava/train/rl/grpo.py:170`, `llava/train/rl/train_grpo.py:366`.

`pg_img`, `pg_txt`, `kl_img` and `kl_txt` are token means within each microbatch,
but the caller averages those means using episode counts rather than the number
or effective weights of tokens of that modality. Unequal reflection lengths
make the resulting value depend on how the same trajectories are split and
sorted into microbatches.

For identical two-episode token losses, the production metric formulas reported
`pg_img=0.0` with microbatch 1 and approximately `0.6` with microbatch 2.
Aggregate per-modality sums and matching denominators across microbatches/ranks.
This affects these diagnostics, not the episode-weighted total loss or optimizer
update; the existing update-invariance test passes.

### 6. [P2] Worker timeout does not bound a complete response read

Location: `llava/train/rl/pixel_reward.py:28`.

`select` limits the wait for the first readable byte, but the following blocking
`readline()` has no deadline. A worker that sends part of a response and then
stalls can hold training beyond `reward_timeout`. Request writes can also block
before the timeout-controlled read is reached.

A fake worker sent `{` and stayed alive for two seconds. With timeout set to
0.1 seconds, `_read` waited approximately 2.02 seconds and eventually raised a
JSON parsing error instead of timing out. Use deadline-aware nonblocking I/O
covering complete requests/responses. Normal full-line worker responses pass
existing transport tests.

### 7. [P2] Variable-width trajectory strips break W&B image-list dimensions

Locations: `llava/train/rl/train_grpo.py:435`, `:419`.

Episode lengths vary, so saved strips are 1024, 1536 or 2048 pixels wide in the
previous run. They are logged together in one W&B image list. W&B 0.26.0 records
common dimensions from the first image and emits the observed unequal-size
warning; display layout can be incorrect. Pad the display strips to a common
width or use a table with a separate image cell per episode. Preserve the exact
individual final-image PNGs used for scoring. This does not affect rewards.

## Scope and interpretation

Read the current core RL files line by line (`rollout.py`, `grpo.py`,
`train_grpo.py`, `dataset.py`, `pixel_reward.py`, `qwen_reward_worker.py`) and
traced their launcher, selected-data, tokenizer/renderer, cache, checkpoint and
W&B dependencies. Reviewed the existing RL tests and GPU smoke script. Legacy
TTS/semantic-reward scripts are separate inactive paths; this report does not
certify their functionality or all vendored neural-network implementations.

No confirmed sign/masking/local-credit bug was found in the tested default
update path. The loss weights every episode equally, assigns its final-image
advantage to sampled semantic/text actions, and updates first-model LoRA only.
A frozen output head, zero-valued centered single-epoch PG surrogate, and
stochastic CFG in the frozen second AR model are intentional choices here.

Remaining operational/design limitations: the GPU smoke has no optimizer step;
CPU tests do not establish exact FlashAttention-2/BF16 sampling-versus-training
numerical parity at full scale. Rendering and Qwen questions are serial per GPU;
first-model KV caches are not reused between phases. Evaluation only persists
per-question/episode details for the selected exemplars, not all evaluated
prompts, and no per-group training reward/advantage records are saved. The
prior 256-prompt baseline cannot be compared directly to the new balanced
32-prompt mean. This review does not establish whether RL improves reward.

Initially, imports blocked on filesystem I/O; they subsequently completed and
both suites ran successfully. No new GPU allocation was requested. The queued
job `59311752` was last observed pending; that is a snapshot, not live status.
